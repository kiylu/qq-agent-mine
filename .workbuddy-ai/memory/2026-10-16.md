### v2 的三处调整

1. **正名升级**：原 C3「主动固化 nudge」→ hermes 真正机制是**每轮后台评审**（fork agent 重放快照，
   产出 memory + skill）；升级为「续接期后台评审」，且明确它是本项目最大缺口（续接期 30 轮零沉淀）。
2. **合并**：原 C2（声明式 Markdown 技能）+ C3（评审）合并为一条主线「学习闭环」——
   载体 + 生产者必须配套。
3. **重排优先级**：按「是否增加模型调用」分层。
   L1 沉淀质量（提示词层，零调用）→ L2 载体（零调用）→ L3 续接期评审（低频调用）
   → L4 治理（技能库 curator + 印象衰减，原 C1 从"第一"下调至此）→ L5 其他（原 C4/C5/C6）。

### 两处反向结论（本次新增，重要）

1. **fork-复用前缀缓存对本项目关闭蒸馏不适用**：关闭条件之一就是"沉默超过缓存 TTL"，
   此时缓存已冷，复用前缀零收益。该技巧**只在续接期评审（缓存热）时才值得抄**；
   关闭蒸馏应维持独立小模型调用。
2. **"什么都不做是失败"不适用群聊**：hermes 该哲学是为通用 agent（几十轮、单轮价值高）设计的；
   QQ 群聊单次价值低、频率高，强行沉淀 = 噪声。**应保留 `skipped-no-content` 出口且标准更严。**

### 追加：L1/L2/L4/L5c 的设计细节讨论（未落文档，待用户确认后再折入）

**核对的代码事实**：
- 记忆工具只有 4 个（`tools.js`）：`memory_append`（印象，需 userId）、`remember_self`（自身状态，≤200字）、
  `memory_query`、`memory_remove` —— **后两个只支持 memberImpression，自身状态无查询/删除工具**。
- 主人判定：`orchestrator.js:813` 消费 `message.owner-check` 能力，返回 `{persona, rules}`；
  提供者 `owner-identity` 技能**默认关**。
- `appendSelf` 上限 40 条；`formatSelfForPrompt(limit=10)` 只取**最近 10 条**（纯插入序）。

**关键结论**：
1. **L1 与 L4b 是同一机制，应合并**。用户补充"按来源定初始 score"比原方案（默认 1.0 + 时间衰减）更好。
   初始分建议：主人+语气强烈 5.0 / 主人普通 3.0 / 群友纠正 2.0 / 自己蒸馏 1.0。
2. **比"存储上限"更紧急的是"注入窗口"**：limit=10 < max=40，重要条目可能因不是最近 10 条而不被注入
   → **注入必须改成按 score 排序**（现为 `slice(-limit)` 插入序）。
3. 纠正的语义属**技能类**（hermes 分工），不该进 memberImpression；L1 先存 `_self.json` 加 `kind: 'rule'`，
   L2 后迁移到 SKILL.md。
4. **回收站**：淘汰不删，移入 `data/memory/backups/evicted.json`（复用现有 backups 模式），
   UI 可查看/恢复；**回收站自身也要设上限**。
5. **L2 缓存问题澄清**：技能索引落点决定后果——system prompt / 工具定义都在 messages 之前，增删 = fresh **一次**
   （一次性，非持续）；只有工具结果/尾部追加才零影响。
   解法：① **批量到会话关闭时 flush**（下一个会话本来就 fresh → 零边际成本，主用）；
   ② 索引走 `list_skills`/`load_skill` 工具（零影响，技能库变大后启用）。
6. **L2 学习频率不可控 → 分层开关**：`autoLearn.enabled`（默认关）/ `createNewSkill`（默认关）/
   `intervalTurns`（默认 8）/ `maxAutoSkills`（默认 10）。
7. **L4a**：扩展页新增「治理建议」区，只读建议 + 确认/忽略，**全程不自动删**，执行前备份。
8. **L5c 微调**：学到的是**风格不是记忆**；数据质量/量/隐私/不可逆都是硬约束。
   现实路径：**先导出 → 先精选 few-shot 示例（便宜、可随时改）→ 人设定稿后再考虑微调**。

## 追加：新增 L4c「全局规则」到改动清单（未实施，仅写方案）

**用户决定的作用域模型**：群聊之间记忆**互相独立**（现状不变）；
只有**主人在私聊里明确要求互通**时，该规则才写进全局层、对所有群生效。

**写进 `doc/change-plan-2026-10-15-hermes-inspiration.md` 的 L4c 要点**：
- 新增 `data/memory/_global/_rules.json`（条目结构沿用自身记忆 + `source`）；
  `_global` 要显式加进 `listChats()` 排除名单（现有正则 `^(group|private)_(\d+)$` 天然不匹配，但要注释说明）。
- **两道闸门缺一不可**：① 必须主人私聊（`kind==='private'` 且 QQ 是主人）；② 必须明确要求互通
  —— 靠**专用工具 `remember_global`**，不靠关键词猜；该工具只在主人私聊可用
  （在 `tool-registry.js` 加可用性判定，做法同 `send_to`，不满足时模型连工具都看不见）。
- **主人判定的硬依赖（关键发现）**：核心配置里**没有** owner QQ —— 它在 `owner-identity` 技能的私有 settings；
  核心只通过 `message.owner-check` 能力问"有没有主人"，而该能力当前返回 `{persona, rules}`，
  **不足以判定"这个私聊是不是主人"**。方案：A（推荐）扩展返回为 `{isOwner, ownerQq, persona, rules}`；
  或 B 核心新增 `owner.qq` 配置。该技能**默认关** → 关闭时功能不可用，UI 要明确给出原因。
- 注入：`formatSelfForPrompt` 前追加【全局规则】段（易变区，不碰稳定前缀）；全局段变化会让所有会话各 fresh 一次。
