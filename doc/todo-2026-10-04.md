  已被实测否定。当前配置本身就是最坏组合——"显式开 thinking + 带 tools + 不回传"，
  实测**无 400**。

### 残留风险（不是现状 bug，是未来复测点）

1. 实测只覆盖**当前渠道/模型**（`api.deepseek.com` + `deepseek-flash`）。

## 决策记录：为什么不改 API 方言

曾讨论"改成 Anthropic Messages / OpenAI Responses 形态以获得思考连续性"，**结论是不改**。

| 变量 | 影响 |
|---|---|
| 换 API 方言 | 只提升**工具轮内**推理连贯性（回传通道从无→有） |
| 换模型 | **这才是"变聪明"的来源**（thinking on/off：AIME 23%→61%、MATH 82%→96%） |

本项目实测：**平均 2.00 轮 API 调用 / 2.08 次工具调用 / 12256 字符提示词**
（12 份会话存档统计）—— 轮次极少、工具极少，正是 reasoning continuity 收益最小的场景。

**结论：想变聪明应该换模型，不是换方言。** 方言改造是纯工程成本换不到对应收益。
（P0 结案后此结论更稳：连"回传"这一项都不需要了。）

—— 用户在 DeepSeek 渠道选"低（快、省 token）"，**实际发出的仍是
`{"thinking":{"type":"enabled"}}`（默认 high）**。
这是**静默失效**：设置显示已保存、参数确实发出、但强度完全没变。

### 修法（已实施）

```js
if (on) {
  params.thinking = { type: 'enabled' };
  applied = true; omitTemperature = true;
}
// effort 与开关并列
if (e && e !== 'off') {
  const mapped = DEEPSEEK_EFFORTS[e] ?? null;   // low→low / medium,xhigh→high / max→max
  if (mapped) { params.reasoning_effort = mapped; applied = true; }
}
```
⚠️ `xhigh` 不在 DeepSeek 合法值里（只认 low/high/max），已用 `DEEPSEEK_EFFORTS`
就近映射。另：`THINKING_BODY_KEYS` 已含 `reasoning_effort`，
降级重试会自动摘掉，**无需额外改**。
（官方还有 `minimal→low`、`ultra→max`，本项目档位未暴露这两个值。）

### 需要用户提供 JSON 记录吗？——**不需要**

Q4 是"发出的请求体缺字段"，**读代码即可定论**。
那份运行期 JSON 能提供的是**佐证**（`raw` 里能看到服务端实际返回的
`reasoning_content` 长度与 `usage.completion_tokens_details.reasoning_tokens`），
不是判据。**只有在验证修复效果时**才需要"修复前/后"两份对比数据。
